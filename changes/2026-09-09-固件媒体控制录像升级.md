## 问题现象

本次工作依据已确认的 IPCam 固件需求，目标板为 i.MX6ULL 搭配 OV5640，当前开发机为 Windows，代码运行环境为 Linux。原有固件只有采集、LCD 显示和基础 MJPEG HTTP 链路，存在以下可复现的固件侧缺口：

1. JPEG 环形缓冲由不同消费者直接取帧，直播客户端、预览和后续录像会争抢同一帧；慢客户端可能拖住采集，异步消费者还有拿到已归还 V4L2 缓冲的风险。
2. V4L2 协商依赖编译期尺寸和固定缓冲假设，没有完整核验 `bytesperline`、`sizeimage`、有效帧长度和驱动帧率；JPEG 槽固定为 256 KiB，不能覆盖质量或规格变化。
3. 显示、采集、编码服务共享进程退出标志，单个子服务停止会影响其它媒体链路；本地预览、熄屏、触摸、补光、拍照和录像没有统一的控制契约。
4. 没有独立的 SD 卡挂载身份校验、拍照收尾、MJPEG AVI 分段、固定时间轴和写入失败处理；录像状态也不能准确区分启动、收尾和错误。
5. 参数保存、日志输出和性能统计不足以支持板端排障，网络接口无法查询统一能力、实际帧率、队列水位和录像状态。

## 问题分析

排查时对照了环形缓冲所有权、V4L2 生命周期、编码消费者、HTTP 客户端和配置保存路径，并按媒体链路逐项检查服务启动与退出顺序。重点确认了以下事实：

1. 采集线程必须在 `VIDIOC_DQBUF` 后立即复制有效帧，不能把 mmap 地址交给异步消费者；显示和直播适合保留最新帧，录像需要独立有界队列。
2. V4L2 的实际行跨度和 `sizeimage` 可能大于宽度乘像素字节数，帧率控制也可能被驱动拒绝，因此能力接口只能公布已验证的基线档位。
3. 录像锁定需要和视频参数及翻转设置共用一个控制入口，不能让 HTTP、GUI 预留接口或 `camctl` 各自修改内部状态。
4. 存储根目录必须确认是独立挂载设备，写入前还要检查空间和收尾余量，临时文件完成同步后再改正式名称。
5. 真实设备节点、背光/补光控制方式、触摸轴和 SD 卡挂载点必须在 Linux 板端探测，Windows 无法替代这一步。

## 问题根因

原链路把“取走一帧”和“观察最新状态”混用，缓冲所有权、消费者背压和服务生命周期没有独立建模；同时缺少承载配置代次、时间戳和实际协商值的公共帧描述。录像、拍照、预览及 HTTP 控制各自缺少明确的状态机和失败语义，导致无法在保持直播的同时独立停止显示或恢复参数。持久化和日志也没有把已生效、已保存、硬件不可用和写盘失败区分开。

### 关键改动说明

1. **帧广播与所有权**：采集端在 V4L2 缓冲仍有效时复制到两条 YUYV 环形缓冲；编码后分别写入直播最新帧缓存和录像有界队列。直播/预览使用 `copy_latest`，录像队列溢出立即记录能力不足并终止当前录制，避免阻塞采集或无限增长内存。
2. **能力和参数**：首版能力接口只公布 640×480、目标 15 fps，JPEG 质量可调 1～100；更高分辨率/帧率在 Linux 板端压力测试前由控制服务拒绝。翻转、预览开关、背光和熄屏时间按持久化语义处理，录像期间锁定分辨率、帧率和翻转。
3. **录像和拍照**：录像复用 JPEG 结果写 MJPEG AVI，按一次手动录像的单调总时长每 300 秒分段，编码缺帧按时间槽重复最近有效帧并计数。文件先使用 `.part` 扩展名，写完索引、同步并排他命名后才报告成功；照片同样独立写入指定 SD 卡。
4. **显示和输入**：本地预览只消费最新 YUYV 副本，按 LCD 比例裁剪后缩放到 RGB565；双指仅在视频区域起始时生效，抬起任一手指结束手势。熄屏关闭背光并暂停本地转换，首次触摸只唤醒，直播和录像持续运行。
5. **控制和观测**：HTTP、GUI 预留契约和 `camctl` 共用控制队列，状态返回目标帧率、采集帧率、输出帧率、队列水位、丢帧、存储和录像状态。日志保留 BCF2 风格字段，每 5 秒汇总媒体性能并限制重复故障刷屏。
6. **停止边界**：各服务使用自己的生命周期标志；HTTP 客户端同时观察进程和 HTTP 服务标志，停止直播时可释放长连接，录像队列在无新帧时轮询停止请求并及时收尾。

## 预期结果

修改后，固件应在能力清单允许的规格下同时提供有线 MJPEG 直播、独立拍照、MJPEG AVI 分段录像、本地预览缩放/平移、方向翻转、背光/补光和统一控制状态。建议切换到 Linux/交叉编译环境后按以下顺序验证：

1. 使用真实板端设备节点和挂载点运行 `make`，再运行 `make ipcam-display-only`；display-only 只验证预览链路，不能替代直播和录像验证。
2. 在 640×480、目标 15 fps 下记录采集/输出帧率、CPU、RSS、四路队列峰值、丢帧和录像重复帧；多客户端直播、预览和录像连续运行 30 分钟。
3. 连续 100 次切换预览、视口和熄屏唤醒，确认不误停录像；验证四种翻转组合，确认 LCD 缩放不改变网络、照片和录像内容。
4. 在录像期间从 HTTP、预留 GUI 接口和 `camctl` 修改分辨率、帧率、翻转，确认统一拒绝；同时确认拍照、JPEG 质量和补光仍按规则执行。
5. 注入缺卡、满盘、拔卡、只读、慢盘、慢客户端、网络断开、摄像头无帧、队列溢出和参数回退失败，核对状态码、临时文件和已完成分段。
6. 检查 AVI 每段可独立播放且总时长与实际录制时长一致，检查旧配置迁移、损坏配置回退、保存失败、日志并发输出、轮转和正常退出收尾。
