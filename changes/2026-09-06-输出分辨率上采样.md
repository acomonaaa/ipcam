## 问题现象

1. 传感器有效分辨率由硬件决定、不可更改（OV5640 DVP 链路 + BSP 驱动约束下的采集分辨率），而客户/产品规格可能要求更高的**输出**分辨率数字，当前编码链路只按采集分辨率 1:1 编码，无法满足。
2. 参数表 [`ipcam_param_t`](../src/core/ipcam_param.h) 没有输出分辨率字段，`/api/config` 无对应键。

## 问题分析

1. **需求本质**：输出分辨率是交付规格，与传感器有效分辨率是两个概念。通过输出端插值上采样满足规格是行业常规（同数码变焦/超分输出），实际画质不变——这是产品定义层面的正当取舍，不是技术投机。
2. **算法选择**：Y 平面（亮度/细节主载体）用双线性——放大 >1.5 倍时最临近有可见块状；色度平面（4:2:2 的低频半分辨率信号）用最临近——双线性收益/代价比不高。
3. **处理位置**：选 planar 域（`unpack → 逐平面缩放 → tjCompressFromYUVPlanes`）而非 packed 域——packed 4:2:2 色度有偶像素对齐约束（display 的 `sx & ~1` 即此），planar 各平面独立缩放无此问题，且与现有 TJSAMP_422 约定无缝衔接。
4. **实现效率**：定点 Q16 插值（避免逐像素浮点）；列映射（x0/小数权重）仅依赖宽度与缩放比，启动时预计算一次；`out == capture` 时旁路（scale_on=0，零额外成本）。
5. **二进制兼容**：param 结构是持久化的 pack(1) 二进制布局。将 `out_w/out_h` 放在原 `reserved[32]` 的前 4 字节、结构体总大小不变——旧配置文件加载时这几字节为 0，恰好等于「跟随采集」默认语义，无需作废。

## 问题根因

- 编码链路只有「采集分辨率 1:1 编码」一条路径，缺少输出端插值环节；参数结构未预留输出分辨率维度。

## 修改方案

### 变更文件列表

### 关键改动说明

1. **插值映射**：源坐标 = `(dst + 0.5) * src / dst - 0.5`（半像素中心对齐），clamp 到 `[0, src-1]`；Q16 定点，列映射启动时预计算。
2. **旁路语义**：`out_w/out_h` 任一为 0 时该维度跟随采集分辨率；两者都等于采集分辨率时 `scale_on=0`，编码路径与改动前逐字节一致。
3. **内存**：缩放缓冲为常驻（启动一次分配：`out_w*out_h + 2*(out_w/2)*out_h + 8*out_w` 字节量级），编码线程每帧只做计算，无每帧 malloc。

## 预期结果

1. 默认（out_w/out_h=0）行为与改动前完全一致：旁路缩放，编码路径零额外开销。
2. `curl -d 'out_w=1280&out_h=720' http://127.0.0.1:8080/api/config` 后重启 daemon，日志出现 `encode scale path: 640x480 -> 1280x720 (Y bilinear, chroma nearest)`，浏览器推流分辨率变为 1280×720（JPEG 尺寸随之增大）。
3. `out_w` 传奇数被拒绝（HTTP 返回 rejected），`/api/status`/`/api/config` JSON 中可见 out_w/out_h 字段。
4. 验证步骤：
