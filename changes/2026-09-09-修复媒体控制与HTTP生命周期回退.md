## 问题现象

1. 同步固件实现到 `dev` 后，`/healthz` 固定返回成功，无法识别 JPEG 输出 ring 已关闭。
2. HTTP 客户端结构体保留了 fd 槽位和条件变量，但实现没有初始化、追踪或主动 shutdown 客户端 fd，停止依赖超时轮询。
3. 帧诊断和 HTTP 生命周期测试仍引用已删除的元数据字段、`ipcam_ring_is_closed()` 和旧 healthz 契约，严格编译无法通过。
4. 4G AT 设备和 PPP profile 散落硬编码，状态接口只调用 `statvfs`，SD 未挂载时可能报告根文件系统空间。
5. AVI 大小限制只统计 JPEG payload，遗漏容器头、chunk header、padding 和索引开销；OTA 64 位文件大小错误路径还存在格式类型问题。

## 问题分析

1. 对比 [`ipcam_stream.c`](../src/services/ipcam_stream.c) 与上一轮生命周期实现，当前版本只维护 `client_cnt`，未维护活动客户端 fd，也没有条件变量唤醒 stop 等待者。
2. [`ipcam_ringbuffer.c`](../src/core/ipcam_ringbuffer.c) 已有关闭状态，但没有公开一致的线程安全查询接口，导致 healthz 无法区分“暂无帧”和“生产者终止”。
3. [`ipcam_control.c`](../src/services/ipcam_control.c) 的存储状态探测与 [`ipcam_record.c`](../src/services/ipcam_record.c) 的挂载校验使用两套逻辑，前者没有比较目录与父目录设备号。
4. 主机测试没有固定 Makefile 入口，且生命周期测试链接真实 stream 实现时缺少控制、录像、显示和熄屏服务桩。

## 问题根因

`7d5fb8d` 将固件媒体控制实现同步到 `dev` 时，HTTP 生命周期和测试侧已有的正确性补丁没有完整保留下来；媒体服务自身的 ring、客户端 fd、状态接口和测试契约因此出现分叉。与此同时，控制状态、4G 启动参数和 AVI 容器大小统计没有复用同一套底层约束。

### 关键改动说明

1. `healthz` 根据全局运行标志和 JPEG ring 关闭状态返回 200/503；输出继续保留 `ok`、`running`、`jpeg_queue` 字段。
2. HTTP 客户端使用 `-1` 空槽、`-2` 预留槽和真实 fd 槽位交接，客户端线程负责最终 close，stop 只负责 shutdown 并等待计数归零。
3. 存储状态通过录像服务统一判断独立挂载设备；未挂载时 `storage_mounted=false` 且 `storage_available=0`。
4. AVI 内部新增包含文件头、chunk header 和 padding 的容器计数，保留原有 payload 统计字段兼容性。
5. 4G 从 `IPCAM_4G_AT_DEV`、`IPCAM_4G_PPP_PEER` 读取运行时覆盖值，未配置时回退到 `IPCAM_4G_AT_DEV`、`IPCAM_4G_PPP_PEER` 默认宏。

## 预期结果

1. `make test-host` 和 `make -B test-host SANITIZE=1` 均通过。
2. HTTP stop 后所有客户端 fd 被主动唤醒并在销毁同步对象前归零，共享 JPEG ring 保持原状态。
