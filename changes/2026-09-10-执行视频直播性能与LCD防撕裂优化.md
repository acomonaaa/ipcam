## 问题现象

基于 `dev` 分支 `5d25a81` 执行 IPCam 视频直播性能与 LCD 防撕裂方案时，代码路径存在以下风险：

1. 显示、直播和录像路径使用定时轮询或复制式取帧，慢消费者可能积累过期帧、覆盖正在读取的槽位，增加单核 Cortex-A7 上的无效 CPU 开销和端到端延迟。
2. YUYV 到预览/JPEG 的路径包含大块中间复制、镜像分支和可扩容 JPEG 输出缓冲；高运动画面会放大内存带宽和分配抖动。
3. MJPEG 客户端没有单帧发送硬截止时间，慢客户端可能长期占住网络线程；JPEG 边界和实际质量也缺少可诊断元数据。
4. framebuffer 双页能力虽然存在实现入口，但启动时没有 page1→page0 的实际自检，pan 失败后的显示故障状态和重试边界不完整，无法把 `direct-fb-pan` 作为无撕裂交付前置条件。
5. 运行日志、`/api/status` 和构建产物缺少统一的实际 revision、阶段 P95、质量状态和队列丢帧信息，现场无法区分旧二进制、过期帧堆积和 LCD pan 失败。

## 问题分析

1. 检查 `src/core`、`src/services`、`src/ui` 和 `src/main.c` 的媒体生命周期后，将 ring buffer、性能窗口、质量状态机和 YUYV 转换拆成可在 Linux 主机上验证的纯逻辑单元；将采集、编码、显示、直播和录像保留为独立消费者，避免通过扩大单一队列掩盖慢路径。
2. 对显示 ring 的借用/释放、关闭唤醒和最新帧快照增加状态约束；确认生产者在显示借用槽期间不能覆盖槽位，HTTP 线程在无新帧时由条件变量等待而不是 10ms 空轮询。
3. 对编码、pan 和 socket 发送统一使用 `CLOCK_MONOTONIC`，用固定容量样本窗口输出平均/P95/最大耗时；质量恢复同时检查无过期帧、编码 P95 小于预算 75% 和采集到编码完成 P95 小于 1.5 帧周期，避免把“暂时未过载”误判为稳定。
4. 目标 BSP/设备节点没有随当前仓库提供，因此没有伪造 Linux 4.1 framebuffer 驱动补丁；应用层只实现能力探测、自检、故障保护和诊断字段，实际 LCD 无撕裂仍必须在 i.MX6ULL 板端验收。

## 问题根因

根因不是单一编码耗时，而是多个消费者在单核平台上同时承担了过期帧处理、整帧复制、阻塞式发送、重复状态探测和不受控的显示提交。与此同时，LCD 是否具备可安全切换的双页 framebuffer 没有在启动阶段被验证，导致应用无法区分“正常双页 pan”和“单页/部分降级复制”。缺少固定窗口指标和实际构建标识又使这些问题难以从现场日志中定位。

### 关键改动说明

1. `ipcam_ringbuffer` 增加 `cond_updated`、单借用者 `read_held` 和单调时钟截止时间。直播客户端使用 `ipcam_ring_copy_latest_wait()`，录像使用 `ipcam_ring_get_timed()`；显示 ring 满时丢新帧而不是覆盖显示线程正在转换的槽。
2. 编码器启动时以 `tjBufSize()` 校验最坏容量，并通过一次 `tjAlloc()` 固定输出存储；编码使用 `TJFLAG_NOREALLOC | TJFLAG_FASTDCT`。自适应质量只在固定质量档位内调整，恢复窗口严格检查低于 75%/1.5 周期并连续 5 次达标。
3. framebuffer 打开后检查 `yres_virtual`、`ypanstep`、`smem_len`，执行 page1→page0 实际 pan 并回读 `yoffset`。运行时 pan 失败只保留 pending page 并按秒重试；LVGL DIRECT 和 LVGL 启动失败后的直接写屏回退都不会用整页 memcpy 覆盖正在扫描的可见页。
4. `/api/status` 保留原字段并增加配置/实际质量、编码/预览/直播统计、发送超时、录像真实/重复帧率、pipeline 和 framebuffer 模式；`/stream.mjpg` 增加 `X-IPCam-Seq`、`X-IPCam-Capture-Ns`、`X-IPCam-Quality`、`X-IPCam-Frame-Bytes`。
5. YUYV 显示 ring 在主入口中按 `宽×高×2 + 64KiB` 分配，并由采集启动阶段用实际 V4L2 `sizeimage` 再次校验，避免行尾 DMA padding 导致静默失败。

## 预期结果

1. 无帧等待、关闭和服务停止能够及时唤醒；显示借用槽不被覆盖，直播和录像互不反压，慢客户端在单帧 500ms 内发送不完时主动断开。
2. 编码、预览、直播、录像和质量状态可从启动日志、`/api/version`、`/api/status` 及 5 秒聚合指标追踪；构建产物带有实际 dirty revision。
3. 在 framebuffer 双页自检成功的板端，LVGL 只提交经过验证的 pan 页面；pan 故障不会回退到覆盖可见页的整页 memcpy，动态视频在 `partial-degraded` 下不会作为可交付模式启用。
4. Linux 主机测试和交叉编译通过后，仍需在实际 i.MX6ULL/Linux 4.1.15 板端完成 640×480@15fps、直播+录像、休眠提示、LCD 外部 120fps 拍摄和 30 分钟耐久验收，才能确认性能数字和无撕裂结果。
