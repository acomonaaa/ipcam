## 问题现象

板端串口能够看到应用启动信息和每 5 秒一次的 `metrics` 汇总，但不能通过日志还原
一次完整的媒体业务生命周期：

1. 采集、LCD、JPEG 编码和网络直播之间缺少明确的首帧及周期帧证据；
2. HTTP 客户端连接/断开、控制命令、录像状态切换、AVI 分段和照片保存基本没有
   业务事件日志；
3. 触摸、熄屏唤醒、背光、LVGL、存储探测等板级动作发生后，串口无法判断动作是否
   被服务接收以及失败在哪一层；
4. 不同源文件共用进程模块名，排查时不容易按 `CAP`、`ENC`、`HTTP` 等业务路径
   过滤日志。

## 问题分析

对照本机 `/home/acomon/bcf2` 工程的 `libmolog`、`mo_media_video.c` 和
`mo_sys.c`：

1. BCF2 的日志库只负责统一时间戳、等级、线程号、模块名、源文件和行号；真正的
   诊断价值来自业务层在启动、首帧、关键帧、状态变化、失败和退出处主动调用
   `MLOG*`。
2. BCF2 视频链路不会把每个普通帧无限刷到串口，而是记录首批帧、关键帧或周期帧，
   同时打印序号、类型、长度和时间戳，使接收端能判断帧是否持续流动。
3. ipcam 原有日志基础设施已经具备等级过滤、文件轮转和串口输出能力，但业务调用
   主要集中在启动/退出和主循环 5 秒统计；`control`、`record`、`touch` 等服务的
   正常路径埋点不足。因此问题是业务日志缺失，不是单纯的串口转发问题。

## 问题根因

ipcam 已有的 5 秒 `metrics` 是聚合健康指标，不能替代 BCF2 风格的业务事件日志。
此前没有把日志模块名和实际服务生命周期绑定，也没有在各消费者拿到首帧、HTTP 会话
发送帧、控制命令完成、录像文件收尾等关键位置记录上下文，所以串口只能说明“线程还
活着”，不能说明“哪一路业务正在正常工作或在哪里失败”。

## 修改方案

### 关键改动说明

1. 采用 BCF2 的“事件日志 + 首批/周期帧摘要 + 汇总指标”三层策略。视频路径不按
   15 fps 无限输出，而是首 30 帧和之后每 30 帧记录，既能看到链路是否持续推进，
   又避免串口 I/O 反过来拖慢单核板端。
2. 采集、显示、编码和 HTTP 日志分别使用 `CAP `、`DISP`、`ENC `、`HTTP` 模块；
   录像、控制、触摸、屏幕等服务也有独立短标签。每条记录仍保留时间、等级、源文件、
   行号和线程号，便于把同一帧在各消费者之间串起来。
3. 正常路径和异常路径均补齐上下文：帧序号/时间戳/长度、ring 结果、客户端 sid、
   request id、录像文件路径、SD 挂载结果以及错误原因都在事件发生处记录；5 秒
   `metrics` 继续保留，用来观察长期吞吐、队列深度和 RSS。
4. display-only 构建也输出编码 stub 日志，避免现场看到跳过 HTTP 时误判为编码线程
   崩溃；模块名只由编译单元声明，未改动的旧调用方仍使用进程级默认模块。

## 预期结果

板端启动后，串口或 `IPCAM_LOG_FILE` 指向的文件应能看到类似以下事件，而不再只有
每 5 秒一条 `metrics`：

```text
INF [CAP ] ... capture service ready ...
INF [CAP ] ... frame no=1 v4l2_seq=... ts=... bytes=...
INF [DISP] ... preview active ...
INF [DISP] ... frame no=1 src_seq=... crop=...
INF [ENC ] ... frame no=1 src_seq=... jpeg=... live_rc=...
INF [HTTP] ... client ... connected ...
INF [HTTP] ... stream session start sid=...
INF [HTTP] ... stream frame: sid=... no=1 seq=... bytes=...
INF [CTRL] ... command done id=... name=...
INF [REC ] ... segment close: file=... frames=... container=...
```
