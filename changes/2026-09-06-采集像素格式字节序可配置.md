## 问题现象

1. 采集协商函数 [`capture_negotiate_yuyv()`](../src/services/ipcam_capture.c) 写死 `V4L2_PIX_FMT_YUYV`，若 i.MX6ULL 4.1.15 BSP 的 CSI 驱动按 UYVY 交付（BSP 驱动常见行为），`S_FMT`/`G_FMT` 校验将失败，采集无法启动。
2. display 与 encode 的字节序处理同样写死 YUYV 偏移（色度在奇字节），即使采集格式改了，下游解包/转色也不跟随，会出现花屏或颜色错乱。
3. 官方例程（RGB565 直采 + memcpy 上屏）与 ipcam 的 YUYV 路线不一致，缺少一份说明「为什么不用官方路径」的架构决策记录，后续联调时容易被误导向 RGB565 对齐。

## 问题分析

1. **字节序差异**：YUYV 为 `Y0 Cb Y1 Cr`，UYVY 为 `Cb Y0 Cr Y1`——Y 与色度的奇偶字节位置互换，帧大小相同（`w*h*2`）。packed 4:2:2 的消费方（display 的转色、encode 的拆平面）都必须知道实际字节序。
2. **配置层级选择**：字节序决定整条链路（capture 协商、display 转色、encode 拆分）的假设，且运行中切换无业务意义，因此放编译期（[`config/ipcam_config.h`](../config/ipcam_config.h)）而非运行时参数，消费者分支可在编译期定死，零运行时开销。
3. **拆分位置复核**：曾考虑把「packed → planar」拆分合并进采集线程的 ring 写入拷贝；通读代码后确认不可取——ring 中是 packed 原始帧，display 与 encode 是两个不同格式的消费者（packed→RGB565 与 packed→planar），在采集线程拆分无法同时服务两路；且现实现中拆分每帧只在 encode 线程做一次、无重复劳动，采集线程保持纯拷贝更利于生产者及时 QBUF。
4. **选型结论**：维持单路 packed 4:2:2 路线（详见 [README 第 10 节](../README.md)）。编码器生态（MJPEG、未来软编 H.264）全在 YUV 侧，i.MX6ULL 无 VPU；转换成本应由次要路径（本地预览）承担。官方 RGB565 例程仅作为 bring-up 硬件验证基线。

## 问题根因

- 采集、显示、编码三处对 packed 4:2:2 字节序做了同一硬编码假设（YUYV），传感器/驱动实际交付格式（YUYV 或 UYVY）未参数化，换 BSP 或传感器配置即联调失败。
- 架构决策（为什么 YUV 而不是 RGB565）未文档化，bring-up 受阻时容易被「官方例程能出图」带偏。

## 修改方案

### 变更文件列表

- [`config/ipcam_config.h`](../config/ipcam_config.h) — 新增 `IPCAM_CAP_PIXFMT`（0=YUYV，1=UYVY），含字节序图示与配置指引
- [`src/services/ipcam_capture.c`](../src/services/ipcam_capture.c) — `capture_negotiate_yuyv()` 改名 `capture_negotiate_pixfmt()`，按配置选择 `V4L2_PIX_FMT_YUYV/UYVY`，失败时打印期望/实际四字符码
- [`src/services/ipcam_capture.h`](../src/services/ipcam_capture.h) — 头注释同步字节序可配置
- [`src/services/ipcam_display.c`](../src/services/ipcam_display.c) — `yuyv_to_rgb565_scaled()` 改名 `yuv422_packed_to_rgb565_scaled()`，按 `IPCAM_CAP_PIXFMT` 编译期分支取 Y/Cb/Cr 偏移
- [`src/services/ipcam_encode.c`](../src/services/ipcam_encode.c) — `unpack_yuyv_to_planar()` 改名 `unpack_yuv422_to_planar()`，支持 UYVY 拆平面；补充「拆分为何留在编码线程」的设计注释
- [`README.md`](../README.md) — 新增第 10 节「采集像素格式选型（架构决策）」

### 关键改动说明

1. **capture**：协商目标 fourcc 由 `#if IPCAM_CAP_PIXFMT == 1` 决定；`G_FMT` 回读不一致时报 `driver did not honor %.4s (negotiated %.4s)`，直接提示改配置还是查驱动。
2. **display**：UYVY 分支下 `u=+0, y0=+1, v=+2, y1=+3`；YUYV 分支维持 `y0=+0, u=+1, y1=+2, v=+3`。缩放、偶数对齐、clamp 逻辑不变。
3. **encode**：UYVY 分支下 `Y=srow[x*2+1]`、`Cb=srow[p*4+0]`、`Cr=srow[p*4+2]`。planar 输出布局（Y 整分辨率 + Cb/Cr 半宽整高）与 `tjCompressFromYUVPlanes` 的 TJSAMP_422 约定不变。

### 中文注释说明（代码类变更必填）

- [`config/ipcam_config.h`](../config/ipcam_config.h) — `IPCAM_CAP_PIXFMT` 注释：两种字节序图示、板上以 `VIDIOC_G_FMT` 为准的配置指引
- [`src/services/ipcam_capture.c`](../src/services/ipcam_capture.c) — `capture_negotiate_pixfmt()` 顶部注释：为何放编译期而非运行时参数
- [`src/services/ipcam_display.c`](../src/services/ipcam_display.c) — `yuv422_packed_to_rgb565_scaled()` 注释改为通用 packed 4:2:2 表述，双分支各标字节序
- [`src/services/ipcam_encode.c`](../src/services/ipcam_encode.c) — `unpack_yuv422_to_planar()` 顶部注释：双字节序布局对照 + 拆分留在编码线程的设计理由

## 预期结果

1. `IPCAM_CAP_PIXFMT=0`（默认）行为与改动前完全一致：YUYV 协商、YUYV 转色/拆分。
2. 板上若驱动按 UYVY 交付：`make CROSS_COMPILE=arm-linux-gnueabihf- IPCAM_CAP_PIXFMT=1`（或在 config 改默认值）后，capture 协商通过，LCD 预览颜色正常、MJPEG 流颜色正常。
3. 驱动不认所选格式时，日志清晰输出期望/实际四字符码，便于决策。
4. 验证步骤：
   - 板上启动后 `MLOGI("camera negotiated: %dx%d fmt=....")` 的四字符码与配置一致；
   - LCD 预览无花屏、肤色正常（字节序错误的典型症状是整体偏蓝绿/偏品红）；
   - 浏览器 MJPEG 流颜色与 LCD 一致。

## 备注（可选）

- 两种字节序均为编译期选择，切换需重编；不做运行时热切（无业务意义）。
- 官方 `25_v4l2_camera`（RGB565 + memcpy）保留在 `ZDYZexample` 作为 bring-up 基线，ipcam 不实现 RGB565 直采路径。
- 后续若实测 UYVY→RGB565 转色占用 CPU 过高，可在 display 引入查表/NEON，或预览降帧降分辨率（不影响推流链路）。
