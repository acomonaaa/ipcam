## 问题现象

摄像头链路已经能够正常工作，但原有运行日志主要集中在启动阶段和线程退出阶段：

1. 只能看到 CSI 节点选择、格式协商和线程启动，缺少“首帧是否真正到达各级消费者”的明确证据；
2. 长时间运行时没有采集、LCD、JPEG 编码和 HTTP 会话的持续帧率与队列状态；
3. 所有日志默认使用进程模块名，串口或 `/var/log/ipcam.log` 中不容易像 BCF2 一样按媒体子模块筛选。

## 问题分析

BCF2 的视频线程会在首帧到达时记录帧序号和大小，并在关键生命周期节点输出模块化日志。
当前 ipcam 已经具备时间戳、级别、源文件、行号和线程号，但采集/显示/编码线程只有
最终累计统计，不能反映运行过程中的实时状态。

如果按每帧打印，会在 640×480 采集时产生大量串口 I/O，反过来影响 i.MX6ULL 单核
调度。因此需要采用“首帧一次 + 每 5 秒汇总”的方式，在诊断价值和运行开销之间取平衡。

## 问题根因

日志基础设施已经能够输出 BCF2 风格的结构化前缀，但媒体链路没有统一的短模块标签，
也没有在首帧和运行期间记录各阶段的吞吐、丢帧、队列深度及 JPEG 大小。因此应用
“能够工作”与“现场能够证明各环节持续工作”之间存在信息缺口。

## 修改方案

### 变更文件列表

- [`src/core/ipcam_log.h`](../src/core/ipcam_log.h) — 增加带显式模块名的 `MLOG*_M` 宏，保留原有日志接口兼容性。
- [`src/core/ipcam_sys.h`](../src/core/ipcam_sys.h) — 将启动库版本日志归入 `SYS ` 模块。
- [`src/main.c`](../src/main.c) — 将主流程生命周期日志归入 `MAIN` 模块，并保持 `IPCAM_LOG_LEVEL` 环境变量优先级。
- [`src/services/ipcam_capture.c`](../src/services/ipcam_capture.c) — 统一 `CAP ` 标签，增加首帧、5 秒采集统计、采集字节数和多类丢帧计数。
- [`src/services/ipcam_display.c`](../src/services/ipcam_display.c) — 统一 `DISP` 标签，增加首帧、显示帧率、跳帧和 ring 深度统计。
- [`src/services/ipcam_encode.c`](../src/services/ipcam_encode.c) — 统一 `ENC ` 标签，增加首帧、编码帧率、跳帧和 JPEG 大小统计。
- [`src/services/ipcam_encode_stub.c`](../src/services/ipcam_encode_stub.c) — 明确打印 display-only 编码空壳模式。
- [`src/services/ipcam_stream.c`](../src/services/ipcam_stream.c) — 统一 `HTTP` 标签，增加流会话首帧、会话帧率和退出统计。
- [`README.md`](../README.md) — 说明日志格式、模块标签、统计周期和验证标准。

### 关键改动说明

1. 日志前缀继续保留时间戳、级别、源文件/行号和线程号；新增模块宏后可看到
   `MAIN`、`CAP `、`DISP`、`ENC `、`HTTP` 和 `SYS `，与 BCF2 的短模块名习惯一致。
2. `capture` 首帧日志包含 V4L2 序号、字节数、驱动时间戳以及 display/encode 两路
   ring 的写入结果；周期统计包含区间帧率、累计帧数、采集字节数、各类丢帧和队列深度。
3. `display` 首帧日志证明 YUYV 已经完成软件转换并写入 framebuffer；周期统计用于
   观察显示消费速度和尺寸异常跳帧。
4. `encode` 首帧日志证明 YUYV 已经生成 JPEG；周期统计包含编码帧率、跳过数量、
   最近 JPEG 大小、区间平均 JPEG 大小和输出 ring 深度。
5. HTTP `/stream.mjpg` 为每个会话分配 `sid`，记录首个发送 JPEG、5 秒会话帧率和
   会话退出总帧数，便于区分编码正常但客户端未连接、客户端慢或网络中断。
6. 采集、显示和编码统计均采用 5 秒节流，不改变原有 ring 所有权和帧处理顺序，
   不按帧向串口刷日志。

## 预期结果

板端启动并运行后，`/var/log/ipcam.log` 或串口应出现类似以下关键日志：

```text
INF [CAP ] ... capture thread start: device=/dev/video1 size=640x480
INF [CAP ] ... first frame: seq=... bytes=614400 ... disp=ok enc=ok
INF [DISP] ... first frame: seq=... bytes=614400 src=640x480
INF [ENC ] ... first frame: input_seq=... jpeg_bytes=... output=640x480
INF [CAP ] ... stats: interval=5.0s fps=... frames=... drop_disp=... drop_enc=...
INF [DISP] ... stats: interval=5.0s fps=... frames=... skipped=... rb=...
INF [ENC ] ... stats: interval=5.0s fps=... encoded=... skipped=... jpeg_avg=...
INF [HTTP] ... stream first frame sid=... seq=... bytes=...
```

预期验证：

1. `lsmod` 仍只有正确的 `mx6s_capture`、`ov5640_camera` 摄像头模块，不加载旧 IPU 模块；
2. 摄像头仍自动选择 `/dev/video1`（以 `name=mx6s-csi` 为依据），LCD 画面和原有推流功能不变；
3. 没有 HTTP 客户端时，`CAP/DISP/ENC` 统计仍持续打印；客户端连接后才出现对应
   `HTTP` 会话首帧和周期日志；
4. 仅有 PxP 或摄像头缺失时，仍安全退出并打印候选节点诊断，不触发内核 oops。
